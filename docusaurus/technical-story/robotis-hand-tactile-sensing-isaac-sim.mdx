## 1. Why Touch in Isaac Sim?

**In short:** ROBOTIS robots learn in Isaac Sim, but the HX5-D20's fingertips could not sense anything there.

More and more robots learn their skills in simulation first and then use them on real hardware. Research teams have started to give simulated robots a sense of touch as well, and report that skills trained this way can carry over to real robots ([Rotating without Seeing](https://arxiv.org/abs/2303.10880), 2023; [Beyond Binary](https://arxiv.org/abs/2605.28812), 2026; [Factorized Tactile Representation and Control](https://arxiv.org/abs/2610.10510), 2026).

ROBOTIS trains its robots in NVIDIA Isaac Sim too, with [Cyclo Lab](https://github.com/ROBOTIS-GIT/cyclo_lab), its robot learning framework. The real HX5-D20 already has a sense of touch: each fingertip carries a 3 × 3 tactile sensor that reports nine values from 0 to 255 ([Hardware Specifications](/docs/systems/hx5_d20/specifications/hardware)). On AI Worker, these readings have already been used by real-robot policies, for example when the hand hides an object from the camera ([ACT with Tactile Sensors](/technical-story/ai-worker-tactile-inference)).

In Isaac Sim, however, the fingertips reported nothing. PhysX, the physics engine inside Isaac Sim, worked out where each finger touched an object, but nothing turned those contacts into the readings a robot gets from its real sensor.

<Still name="cup_no_touch" alt="AI Worker holds a cup in Isaac Sim while the tactile panel for its fingertips stays empty">
  AI Worker holds a cup in Isaac Sim, but every fingertip reading stays empty.
</Still>

So we built that missing sensor.

## 2. What We Built

**In short:** A virtual tactile sensor on each fingertip turns the contacts PhysX already computes into 5 × 3 × 3 readings, laid out like the real hand's.

We gave every fingertip of the simulated HX5-D20 a virtual tactile sensor. It adds no new physics. It reads the contacts that PhysX already computes and turns them into readings laid out like the real sensor's: five fingers, nine cells each, one value from 0 to 255 per cell.

Isaac Sim and Isaac Lab already include contact sensors. They report one total force for a whole body, or a raw list of contact points. Neither is laid out like the real HX5-D20, which reports nine values per fingertip, so the simulated sensor sorts each touch into cells.

<Still name="system_overview" alt="Two rows: on the real HX5-D20, a touch reaches the tactile sensor and its 5 by 9 readings go to a ROS 2 topic; on the HX5-D20 in Isaac Sim, PhysX contacts reach a virtual tactile sensor and its 5 by 9 readings go to a heatmap">
  The real hand and the simulated hand side by side: in Isaac Sim, a virtual sensor turns PhysX contacts into readings in the real sensor's layout, 5 × 3 × 3 values from 0 to 255.
</Still>

The sensor is part of Cyclo Lab. Section 3 shows how to run it, and Section 4 explains how it works.

Five words are used throughout this story:

| Term | Meaning |
| :--- | :--- |
| **Pad** | The sensing area on the inside of a fingertip. |
| **Cell** | One of the pad's nine squares, also called a *taxel*. |
| **Contact point** | A point where PhysX finds the fingertip touching something. |
| **Reading** | A cell's value from 0 to 255, in the same range as the real sensor's. |
| **Physics step** | One update of the simulation. Isaac Sim moves the world forward in short slices of time, 120 per second in the demo. |

## 3. Start Guide

**In short:** One command tries the sensor without any hardware. One added option turns it on during the VR teleoperation of AI Worker, and two settings add it to your own scene.

### 3.1 Requirements

- A Linux PC with an NVIDIA GPU and its driver.
- Docker with Docker Compose, and the NVIDIA Container Toolkit.

These are the requirements of Cyclo Lab itself ([Installation](https://github.com/ROBOTIS-GIT/cyclo_lab/tree/feature-isaacsim-6.1.0#installation-docker)). Run the steps at the PC itself, not over SSH, so that the Isaac Sim window can open.

The sensor is on Cyclo Lab's branch for Isaac Sim 6.1, so clone that branch.

```bash
  https://github.com/ROBOTIS-GIT/cyclo_lab.git
```

```bash
git submodule update --init --recursive
```

### 3.5 Use It in Your Own Scene

The sensor is an Isaac Lab sensor, so it can go into any Isaac Lab scene with an AI Worker SH5. Two settings turn it on: the robot reports the contacts of its fingertips, and each hand gets a `HandTactileCfg`.

```python
from cyclo_lab.assets.robots import FFW_SH5_CFG
from cyclo_lab.sensors import HandTactileCfg
from isaaclab.scene import InteractiveSceneCfg
from isaaclab.utils import configclass

@configclass
class MySceneCfg(InteractiveSceneCfg):
    robot = FFW_SH5_CFG.replace(
        prim_path="{ENV_REGEX_NS}/Robot",
        spawn=FFW_SH5_CFG.spawn.replace(activate_contact_sensors=True),
    )
    tactile_left = HandTactileCfg(
        prim_path="{ENV_REGEX_NS}/Robot", hand="left", debug_vis=True
    )
    tactile_right = HandTactileCfg(
        prim_path="{ENV_REGEX_NS}/Robot", hand="right", debug_vis=True
    )
    # ... your table, objects and lights
```

Objects need nothing extra. When the simulation starts, the sensor finds every rigid body and collider in the scene, so the fingertips can feel any rigid object you add. An object added while the simulation runs is found at the next start. `debug_vis=True` opens the heatmap windows.

To read the values in your code:

```python
# Shape: (environments, 5, 9)
readings = scene["tactile_left"].data.cell_readings.torch
# Environment 0, index finger, cell 5
index_center = readings[0, 1, 4]
```

Fingers and cells are counted from 0, with the thumb first, so the index finger is 1 and cell 5 is 4.

For VR, add your objects to the class `SH5BringupSceneCfg` in `scripts/sim2real/bringup/sh5_dds_bringup.py`.

## 4. How It Works, Step by Step

**In short:** After every physics step, five steps turn the contacts on a fingertip into nine readings.

The code is in Cyclo Lab, under `source/cyclo_lab/cyclo_lab/sensors/hand_tactile/`.

### 4.1 Step 1 · Find the Contacts

PhysX already knows where things touch. For every contact point it reports three things: where the point is, which way the two surfaces push on each other, and the *impulse*, the push it took to keep the two bodies apart during that step.

PhysX places a few contact points where two shapes meet. In our scenes, a small ball pressing a pad gives one point per step, and the side of a can usually gives three. PhysX also reports points where two surfaces are close but do not press yet; they carry no force and add nothing to a reading.

After every physics step, the sensor reads the contact points of each fingertip. There is one contact report per fingertip, not one per cell. The cells come from where the points land, in Step 2.

<Still name="contact_point" alt="Thumb and index pads on a see-through marker, with the contact point and the press direction labeled">
  Where a pad touches the marker: the contact point.
</Still>

### 4.2 Step 2 · Which Cell?

Each pad carries a 3 × 3 grid fixed to the fingertip, so it moves with the finger: a 15 mm square made of nine 5 mm cells, laid on the fingertip's outer surface along the pad's visible 3 × 3 layout. The cells are numbered row by row, from the row nearest the fingertip's tip (cells 1–3) to the row nearest the finger (cells 7–9). Section 6 compares where touches land with the real hand.

PhysX reports contact points from anywhere on the fingertip. The grid keeps only those on the pad and sorts them into cells, in two checks:

1. **Which cell, seen from the front.** Looking straight at the pad, like a photo, the point lands in one of the nine cells. A point outside the 15 mm square is left out.
2. **On the pad's surface.** The point must also lie no more than 1 mm below the pad surface, so a touch elsewhere on the fingertip does not count. This check follows the curve of the pad, so the curved cells on the sides count too.

Why allow 1 mm? PhysX works on simplified collision shapes and reports a contact a little before two surfaces meet, so a contact point can sit slightly off the visible surface. The 1 mm allows for that small gap.

<Clip name="which_cell" label="Animation: a touch lands in cell 4 seen from the front; in a cut through the pad, a 1 mm skin follows the curve">
  From the front, a touch lands in cell 4, and one outside the 15 mm square is left out. In a cut through the pad, the 1 mm skin follows the curve, so the touch near the curved edge still counts.
</Clip>

One more rule is a safety net for rare cases. In our tests, the two checks above already left out touches on the side of the finger, such as a bump against a neighboring finger. A contact on the pad can still push in at a steep angle, though this was rare. The whole pad uses one direction, the pad direction: the way a straight press comes in. A push that comes in more than 45° off it is left out. The 45° limit lies halfway between a straight press (0°) and a push along the side of the finger (90°). Like the 1 mm depth, it is a setting chosen for the simulation, not a sensor specification.

<Clip name="side_of_finger_rule" label="Animation: pushes on a cut through the fingertip count within 45 degrees of the pad direction and are left out beyond it">
  Pushes at the pad's center (0°) and on its curve (24°) count. A push from the side of the finger (77°) is left out; that spot is also outside the 15 mm square.
</Clip>

### 4.3 Step 3 · How Hard?

Dividing a contact's impulse by the length of the step gives its force. We count only the part of that force that presses straight into the pad, as a pressure sensor measures pressing. Friction, the part of a push that slides along the surface, is left out: PhysX reports it separately, and the sensor does not read it.

Friction itself is not measured, but sliding still shows up: a pad that slides while it presses moves its press from cell to cell, so the lit cell moves along with it.

```text
force of a point = |impulse · pad direction| / step time
```

<Still name="how_hard" alt="A slanted push on the center of the pad, split into a part along the pad direction, counted, and a part along the surface, left out">
  A slanted push, split in two: the part that presses into the pad counts; the part that slides along it, friction, is left out.
</Still>

The dot (·) in the formula keeps only the part of the impulse that points along the pad direction. On the flat middle of the pad, the surface faces the pad direction, so a straight press counts in full. On the curve, the surface tilts away from it, and the dot keeps the force times the cosine of the tilt. The cells on the two sides of the pad (1, 3, 4, 6, 7 and 9) tilt by about 24–26°, so a press straight into their surface counts at about 90%. Cell 2, at the tip, tilts about 11°, and cells 5 and 8 are flat. This share comes from the geometry; it is not a tuned factor. Beyond 45°, the side-of-finger rule leaves the push out altogether.

The force of a point is then spread over the cells around it. PhysX reports a touch as points between rigid shapes, and each point falls in a single cell. In the can touch of Section 6, though, the real hand lit two neighboring cells where the simulated touch sat near their border. So each cell takes a share by how far the point is from the cell's center, following a Gaussian (a bell curve) with a standard deviation of 1.5 mm, and the shares add up to the point's force. A point at a cell's center keeps about 98.5% in that cell, about 0.4% goes to each cell beside it, and the diagonal cells, farther away, get almost nothing. A point 0.5 mm from a border splits about 75/25. The width is not a measurement of the real pad: it was set against one recording of the can touch in Section 6.

<Clip name="spread_over_cells" label="Animation: a touch at the center of cell 5 keeps almost all its force there; moved near the border with cell 6, it splits about 75/25 between the two cells">
  One touch's force shared among the cells: at a cell's center it stays in that cell, and near a border it splits between the two cells.
</Clip>

Each cell then adds up its shares from all the contact points. That gives one force per cell, so nine forces per fingertip, in newtons. With no contact point on the pad, every cell gets 0:

```text
force of a cell = sum over the contact points of
                  force of the point × share of the cell
```

### 4.4 Step 4 · From Force to Reading

The real sensor does not report newtons. It reports a value from 0 to 255. Each cell's force is therefore converted with an approximate force-to-reading scale for simulation ([Section 5](#5-matching-the-scale-to-the-real-sensor)), and capped at 255. The forces in newtons are kept as well.

### 4.5 Step 5 · Color It Like the Real Viewer

The heatmap colors each reading with the same rule as ROBOTIS's tactile viewer for the real hand (see [Tactile Feedback Grasping](/technical-story/robotis-hand-tactile-feedback-grasping)). The rule brightens small readings so that light touches stay visible, and shows every reading above a ceiling, set by `color_max`, in full color. With the same `color_max`, a simulated and a real heatmap share one color scale. The sensor's heatmap uses the viewer's default, 125; the VR bringup uses 60 (Section 7).

The heatmap also smooths what it shows: a cell's color settles within about 0.1 s of a change, about as fast as the real viewer. This smoothing changes the picture only; the readings stay as computed.

Because of the spread in Step 3, a touch near the border between two cells lights both, as the real hand did in the can touch of Section 6. A touch at a cell's center lights only that cell.

<Still name="heatmaps_sim_real" maxWidth="360px" alt="A simulated and a real heatmap window side by side, both lighting cells 7 and 8 of the index pad">
  A heatmap from an earlier version of this sensor (left) and the real hand's viewer (right), during the can touch of Section 6. Both color readings with the same rule; the earlier version's brightness was tuned on this recording.
</Still>

<summary>The numbers behind each step</summary>

| Step | Setting | Value | In the code |
| :---: | :--- | :--- | :--- |

### 4.6 What Comes Out

After every physics step, each hand gives:

| Item | What it is |
| :--- | :--- |
| Layout | 5 fingers × 9 cells, from the thumb to the little finger, in the same finger order as the real hand's sensors |
| Cell numbers | 1–9, row by row from the fingertip's tip, as in Step 2 |
| Readings | One value from 0 to 255 per cell, on an approximate scale for simulation (Step 4) |
| Forces | One force in newtons per cell (Step 3), kept for analysis; the real sensor has no such value |
| No touch | Every reading and force is 0 |

In an Isaac Lab script, they are the sensor's `data.cell_readings` and `data.cell_forces`, each with one 5 × 9 block per environment.

On the real hand, the readings arrive on the ROS 2 topics `/left_hand/finger_pressures` and `/right_hand/finger_pressures` ([robotis_hand](https://github.com/ROBOTIS-GIT/robotis_hand)). The simulated sensor does not publish these topics; its readings stay inside Isaac Lab.

## 5. Matching the Scale to the Real Sensor

**In short:** The scale from force to reading was set from a measurement of the real sensor. On the cell that was checked, a press reads close to what the real sensor read for the same force.

:::warning
This scale only turns simulated forces into simulated readings. It is a rough match, so do not use it the other way, to estimate forces from the real sensor's readings.
:::

This matters for learning: the aim is that a skill trained on simulated readings meets similar numbers on the real robot. No skill has been trained and tested this way yet. The scale was set in three steps.

| Step | What was done |
| :--- | :--- |
| 1. Measure | The real sensor was pressed with known forces, and its readings were recorded. |
| 2. Set | A force-to-reading scale for Isaac Sim was set from those recordings. |
| 3. Check | In Isaac Sim, one cell was pressed with set forces, and its readings came close to the real sensor's at those forces. |

In Cyclo Lab, this scale is the sensor's default. It is a first match, from one measurement and checked on one cell.

  The scale is set from the real sensor, then checked in Isaac Sim.
</Still>

## 6. Does It Light the Right Cell?

**In short:** In three checks, the touched cell lit up, and the simulated and the real hand lit cells in similar places.

| Check | What was done | Cells that lit up |
| :--- | :--- | :--- |
| Each cell | In Isaac Sim, a small ball pressed the center of the nine cells of the index pad in turn. | Only the pressed cell, nine times out of nine. |
| Same commands as the real hand | The simulated and the real left hand pressed a can with the index, middle and ring fingers in turn, with the same joint commands. | Cells 7 and 8 of each of the three pads, on the simulated and the real hand. |
| A new motion | With the settings unchanged, the simulated and the real hand pinched a 15 mm marker. | Mostly cell 4 of the thumb pad and cells 1 and 2 of the index pad, on the simulated and the real hand. |

These checks look at where a touch lands, not at how hard it presses. The can and the marker were recorded with an earlier version of the sensor, before the scale in Section 5 was set, when the spread applied to the picture only. Replayed through the current scale and spread, the recorded contacts light the same cells. The width of the spread was tuned on the can recording; the marker was not used for tuning.

## 7. On a Whole Robot: AI Worker in VR

**In short:** The same sensor runs on all ten fingertips of AI Worker while an operator drives it in VR.

AI Worker carries two HX5-D20 hands. With the tactile option of Section 3, both hands compute their fingertip readings live during VR teleoperation and show them in heatmap windows ([AI Worker SH5 Isaac Sim VR Teleoperation](/technical-story/ai-worker-isaac-vr-teleoperation)).

Hands in VR touch objects at many angles, so the VR bringup checks the pads more loosely than Section 4: a contact point may lie up to 3 mm below the pad surface instead of 1 mm, and a push may come in up to about 72° off the pad direction instead of 45°. Its heatmaps also show light grasps brighter, with `color_max` 60 instead of the real viewer's default 125. The scale from force to reading, the spread and the heatmap's smoothing are the same.

## 8. Limitations

**In short:** Where touches land has been compared with the real hand in a few touches; how closely the readings match has been checked only in part.

| Limitation | What it means |
| :--- | :--- |
| The simulated hand's strength is not matched | Given the same joint command, the simulated fingers may press harder or softer than the real ones, because the finger motors in Isaac Sim have not been tuned to the real hand. The same command can then give different readings, even on a matched scale. |
| One direction for the whole pad | Every cell measures along the same pad direction (Section 4.3), so a press made straight into a curved side cell counts at about 90%. If each cell of the real pad measures along its own surface instead, the real side cells would read a little higher than the simulated ones. This has not been checked. |
| The spread is an estimate | Its width was set against one recording, not measured on the real pad, and it does not change with how hard a press is. PhysX still reports a touch as points, so the spread does not follow the shape of the object. |
| Cell positions are approximate | The grid follows the pad's visible layout on the fingertip's surface. Which point on the surface reaches which cell of the real pad has been checked only through the touches in Section 6. |

## 9. Conclusion

At the start of this story, the HX5-D20's fingertips could not sense anything in Isaac Sim. Now each fingertip reports readings in the real sensor's layout: 3 × 3 cells per pad, on an approximate scale for simulation, and colored by the real viewer's rule. In our checks, the cells that lit up were close to those on the real hand. In Cyclo Lab, one command starts a demo without any hardware, and one option turns the sensor on during VR teleoperation.

**A first step toward robots that learn with touch in Isaac Sim.**
